# AGENTS.md — LifeHub

> Єдине джерело правил для всіх AI-агентів (Claude Code, Codex, Cursor тощо). `CLAUDE.md` лише підключає цей файл — правила редагуй тут.

LifeHub — персональний вебзастосунок (PWA) для одного користувача: фінанси, бюджети, цілі, покупки, **планування меню**, запаси продуктів, подорожі, AI за запитом. Валюта — тільки UAH, інтерфейс — тільки українською, операції вносяться вручну.

Спілкування з користувачем — українською.

## Робочий процес (обов'язковий для кожної задачі зі зміною коду)

### 1. Контекст — повністю, не з пам'яті
- Перед планом заново прочитай **повністю** потрібні файли: задачу в DEVELOPMENT_ROADMAP.md, пов'язані розділи PRODUCT.md / USER_FLOWS.md / TECHNICAL_PLAN.md і весь код, який змінюватимеш або який його викликає.
- Не покладайся на пам'ять попередніх сесій, стислі підсумки чи фрагменти: якщо згадуєш файл, функцію, поле чи правило — спершу перевір, що воно існує й виглядає саме так зараз.
- Чогось не вистачає або дані суперечать одне одному — спитай, а не домислюй.

### 2. План — до коду, з підтвердженням користувача
Перш ніж змінювати файли, покажи план і **дочекайся явного «так»**. План містить:
- як ти зрозумів задачу (своїми словами) і що є результатом;
- що **не** входить у задачу;
- які файли створиш або зміниш і що саме в них;
- які бізнес-правила (BR-…) і сценарії зачіпаються;
- які тести додаси і які наявні запустиш;
- ризики, припущення та відкриті питання.

Без підтвердження плану код не пишеться. Якщо під час роботи план доводиться змінити — зупинись, опиши зміну й знову отримай підтвердження.

### 3. Новий код не ламає старий
- Змінюй лише те, що потрібно для задачі; не рефактори й не «покращуй» сусідній код без погодження.
- Змінюєш публічний API модуля (`index.ts`), схему БД чи спільний код `shared/` — знайди всіх користувачів і онови їх у тій самій задачі.
- Не видаляй, не вимикай (`skip`) і не послаблюй наявні тести, щоб вони пройшли. Тест падає — виправляй код або обговори з користувачем, чи змінилась вимога.
- Міграції — лише додавання нових; дані користувача не повинні губитися.

### 4. Тести для нового функціоналу
- Нова або змінена бізнес-логіка — нові тести на неї (успіх, помилки, крайові випадки, відповідні BR).
- Під час роботи запускай тести цього модуля **і сусідніх** — тих, що від нього залежать або від яких залежить він (TECHNICAL_PLAN.md §3.3; наприклад, зміни в `finance` → також `shopping`, `travel`, `goals`, `dashboard`).
- Перед завершенням — повний прогін `lint`, `typecheck`, `test` (+ `test:e2e`, якщо зачеплено сценарій). У звіті — що саме запущено і з яким результатом.

### 5. Рев'ю незалежним субагентом
- Після реалізації й зелених тестів запусти **окремого субагента зі свіжим контекстом** для рев'ю.
- Дай йому диф, текст задачі з roadmap і посилання на відповідні документи — **не** свої висновки й не пояснення, чому все правильно.
- Він перевіряє: відповідність задачі й плану, бізнес-правила (особливо гроші, подвійний облік, BR-1…BR-15), регресії, межі модулів, якість і повноту тестів, безпеку.
- Кожне зауваження перевір сам; підтверджені — виправ і знову прожени тести. У звіті користувачу перелічи, що знайдено, що виправлено і що свідомо залишено (з причиною).

### 6. Звіт
Наприкінці: що зроблено, які файли змінено, результати тестів і рев'ю, що не зроблено або не перевірено, оновлена документація.

## Стек

Next.js (App Router) · React · TypeScript strict · Tailwind · shadcn/ui · Server Actions / Route Handlers · PostgreSQL · Prisma · Zod · React Hook Form · Recharts · Vitest · Playwright · Auth.js · Claude API (опційно).

Не додавай без погодження: окремий бекенд, мікросервіси, Redis, черги, GraphQL, Redux, нові великі залежності.

## Архітектура

- Modular monolith: `src/modules/<module>/{domain,repository,services,actions,schemas,components,index.ts}`, спільне — `src/shared/` (money, units, dates, db, auth, result, ui).
- Модулі імпортують один одного **лише через `index.ts`**. Модуль пише тільки у свої таблиці; чужі — через публічний сервіс власника.
- `domain/` — чисті функції без I/O. `repository/` — лише Prisma. Server Action: сесія → Zod → сервіс → `ActionResult`.
- Багатокрокові зміни — в одній транзакції БД (`tx` передається між сервісами).
- Похідні показники (баланси, факт бюджету, прогрес цілей, факт подорожі) не зберігаються — обчислюються з джерельних даних SQL-агрегаціями.
- Кожна Server Action і Route Handler перевіряє сесію (middleware — не єдиний захист).

## Гроші й фінансові дані

- Суми — **цілі числа в копійках** (`Int`). Ніякого `parseFloat`, `Number()` для сум, `Float` чи float-арифметики. Тільки `shared/money` (`parseUah`, `formatUah`).
- Єдиний реєстр `Transaction` (`income` / `expense` / `transfer`); кожна реальна операція — рівно один запис. Сума > 0, тип визначає напрямок.
- Перекази не є доходами чи витратами. Поповнення цілей — не транзакції. Бюджети, планові покупки, вартість меню, прогнози — план, не факт.
- Travel, Shopping, Food, Pantry не мають власного обліку грошей: лише необов'язкові FK на `Transaction` (`tripId`, `purchaseId`). Оформлення покупки = одна транзакція; оновлення Pantry транзакцій не створює.
- Рахунки, категорії, продукти з посиланнями — лише архівування, не видалення.
- Дати подій — `DATE` у поясі `Europe/Kyiv`; межі місяців і тижнів (пн–нд) — через `shared/dates`.
- Створення записів з форм — ідемпотентне (`clientRequestId`).

## Меню, рецепти, інгредієнти

- Планування меню — **P0, ядро MVP**. Не спрощуй його до текстового календаря й не переноси на пізніше.
- Інгредієнт = продукт із каталогу + кількість (`Decimal`) + одиниця. Об'єднання — за `(productId, розмірність)`, не за текстом.
- Конвертація лише в межах розмірності (г/кг; мл/л/ч. л./ст. л./склянка; шт). Несумісні — окремі рядки. «За смаком» не підсумовується.
- Кількість для страви = кількість у рецепті × порції плану / базові порції рецепта.
- Нестача = max(0, потреба − наявне в Pantry (неспливле) − «вже є вдома»).
- Формування списку з меню не пише в БД до підтвердження і не створює фінансових транзакцій. Позиції списку — знімок.
- Рецепт, що використовується в меню, — лише архівування.

## Правила внесення змін

- Працюй у межах однієї задачі roadmap; не додавай функцій поза MVP_SCOPE без погодження.
- Кожна задача roadmap — в окремій сесії агента з власним git worktree і гілкою `day-NN-<коротко>` (наприклад, `day-02-ui-shell`). Злиття в `main` — лише після перевірки й дозволу користувача.
- Схема БД змінюється лише новою міграцією Prisma; застосовані міграції не редагуються. CHECK-обмеження — сирим SQL у міграції.
- Тексти інтерфейсу — українською; формат `1 234,56 ₴`, `ДД.ММ.РРРР`.
- UI — за [docs/DESIGN.md](docs/DESIGN.md): лише токени теми (без довільних hex у компонентах), обидві теми, спільні компоненти з `src/shared/ui`. Новий екран без макета — спершу короткий макет або опис у DESIGN.md і підтвердження користувача.
- Перевіряй UI на desktop і 375 px, у світлій і темній темі.
- Без секретів у коді; змінні середовища описуй у `.env.example`.
- Не роби git commit/push без прохання користувача.

## Тестування

- Перед завершенням задачі: `lint`, `typecheck`, `test` (і `test:e2e`, якщо зачеплено сценарій).
- Нова доменна логіка — з unit-тестами (Vitest, поруч із кодом). Бізнес-правила BR — integration-тестами з тестовою БД. Ключові сценарії — Playwright.
- Помилку в розрахунках спочатку відтвори тестом, потім виправляй.

## Документація

- Неоднозначність — не вигадуй поведінку: запиши як Open Question (PRODUCT.md §13 або TECHNICAL_PLAN.md §18) і спитай користувача.
