# ADR 0002 — PostgreSQL для розробки й тестів — гілки Neon

- Статус: прийнято
- Дата: 2026-11-26 (roadmap, день 3)
- Пов'язано: [TECHNICAL_PLAN.md](../TECHNICAL_PLAN.md) §1, §3.1, §7.4, §12, §18 (TD-2)

## Контекст

План передбачав локальний PostgreSQL у Docker (`docker-compose.yml`). На комп'ютері розробки Docker не встановлено. Розглядали: Docker Desktop (важкий, WSL2, права адміністратора), нативний PostgreSQL для Windows (інсталяція, служба) і хмарний Neon. Користувач хоче згодом користуватися застосунком з телефона після деплою на Vercel, а для цього потрібна хмарна база — Neon уже є рекомендацією TD-2.

## Рішення

- Один проєкт Neon `lifehub`, регіон AWS Europe Central 1 (Frankfurt), PostgreSQL 18, гілки:
  - `production` (за замовчуванням) — майбутні реальні дані; не використовується до деплою (тиждень 15–16);
  - `dev` — база розробки, змінна `DATABASE_URL`;
  - `test` — база integration-тестів, змінна `TEST_DATABASE_URL` (дані стираються тестами).
- Для розробки й міграцій — **direct**-рядок підключення (без connection pooling): `prisma migrate` потребує прямого з'єднання. Pooled-рядок для застосунку на Vercel налаштовується разом із деплоєм.
- Застосунок підключається через `@prisma/adapter-pg` (node-postgres по TCP), тож код не прив'язаний до Neon: будь-який PostgreSQL працює з тим самим кодом.
- `docker-compose.yml` не додаємо.
- Рядки підключення — лише у `.env` (у `.gitignore`); шаблон — `.env.example`.

## Наслідки

- **Плюси:** нічого не встановлювати; той самий провайдер, що й у продакшні; гілки Neon дешево скидаються («Reset from parent»).
- **Мінуси:** без інтернету розробка з БД неможлива; затримка мережі уповільнює integration-тести; безкоштовний план має ліміти обчислень і «засинання» compute (перший запит після простою повільніший).
- **Безпека:** `prisma migrate reset` і тести виконуються лише на `dev`/`test`; рядок `production` ніколи не записується в `.env` розробки.
- **Повернення:** перейти на локальний PostgreSQL можна, змінивши лише `DATABASE_URL`/`TEST_DATABASE_URL`.
